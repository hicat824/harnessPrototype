## 1. 结论

**当前 D6-04 是真实的模型调用决策错误，测试没有误判。Fake Agent 缺少参数来源的执行前校验，使这个错误到达了 Mock API。测试本身也有评估与诊断设计上的不足，但它们不是本次失败的直接原因。**

应分别看待三个层次：

| 层次 | 本次情况 | 判断 |
|---|---|---|
| 最终回答 | 正确追问 engine_code，结构和关键字段正确 | 通过 |
| 模型调用决策 | 缺参时编造 `__MISSING__` 并请求工具 | 不通过 |
| 执行边界 | 仅检查格式、重复、次数及先前错误，未检查参数来源 | 需要补强 |

不建议继续反复叠加提示词，也不建议放宽成“最后追问正确就算通过”。

## 2. 本次证据

报告：[pytest-68/day6_real_llm_report.json](/tmp/pytest-of-xumaozhou/pytest-68/test_day6_real_llm_evals0/day6_real_llm_report.json)。

| 项目 | 结果 |
|---|---|
| 业务用例 | 9/10 通过，仅 D6-04 失败 |
| 最终回答字段检查 | 10/10 通过 |
| 工具轨迹检查 | 9/10 通过 |
| 模型请求 | 14 次 |
| SDK 记录 Token | 输入 18099，输出 1235，总计 19334 |

“最终回答字段检查”按当前报告中的 answer_schema、status、error_code、task_ids、total、missing_fields、source、truncated、summary_facts 汇总，属于机器初筛，不代表所有自然语言事实已经过人工核实。“工具轨迹检查”按 tool_choice、tool_arguments、no_blocked_calls 汇总。

D6-04 的用户输入：

```text
按流程编码列出最多 3 条任务，但流程编码还没有提供。
```

模型先请求：

```json
{
  "name": "query_tasks_by_engine",
  "arguments": {"engine_code": "__MISSING__", "limit": 3}
}
```

工具实际返回 `status="empty"`、`data={"items": [], "total": 0}`、`source="mock_task_api"`。然后模型回答：

```json
{
  "status": "needs_input",
  "summary": "还缺少流程编码（engine_code），暂时无法列出任务。请提供流程编码，我会按该编码返回最多 3 条任务。",
  "task_ids": [],
  "total": null,
  "source": null,
  "truncated": false,
  "error_code": "MISSING_PARAMETER",
  "missing_fields": ["engine_code"]
}
```

本次 `tool_call_count=1`、`blocked_call_count=0`、模型请求 2 次。说明最终追问发生在一次无依据查询之后。工具记录中已有实际业务结果，可以确认该请求到达了 MCP 工具执行流程。

失败检查项为 `tool_choice`、`tool_arguments`、`tool_results`、`tool_data`；它们主要由同一次错误调用引起，不能当成四个独立故障。`counts=true` 只表示记录的调用数与 Trace 长度一致，并不表示符合“本用例应调用 0 次”的要求。

本次没有 ModelBehaviorError，也没有护栏中止。新增异常诊断分支没有触发是符合实现的，不能据此认定异常记录失效。

## 3. 这几次改动及实际效果

以下按会话中的处理顺序整理；较早报告已被 pytest 临时目录清理的部分，依据当时用户日志和会话中的报告读取结果，不宣称当前仍可重新读取原文件。

| 改动 | 解决的问题 | 效果与边界 |
|---|---|---|
| 完成三个 Day6 核心函数 | 结果字典读取、检查优先级、局部变量覆盖、缺失返回、usage/耗时、受控异常 | 基础流程可以通过离线验收；不能证明真实模型会正确选工具 |
| 明确 needs_input 的字段赋值 | 模型正确追问却返回 error_code=null | 后续缺参回答的字段检查通过；不能保证追问前不调用工具 |
| 强调工具错误后结束 | 模型在 CONNECTION_ERROR/NOT_FOUND 后继续请求工具 | 某些轮次通过，后续仍出现失败；提示词没有构成可靠执行边界 |
| 完善异常记录 | ModelBehaviorError 只保留类型，无法定位 | 记录错误说明、堆栈、模型响应、工具 Trace 和已统计 usage；测试观察器兼容 SDK 清理异常 run_data 的情况 |
| 接入 tool_use_behavior | 工具业务错误后模型再次查询 | 当前报告中 403、404、超时、连接错误及无限重查要求均正确结束；这些错误用例各仅请求模型 1 次 |
| 补充缺参规则与工具说明 | 模型填入占位 engine_code | pytest-67 与 pytest-68 仍出现同一占位调用；说明仅补说明尚未解决这条调用决策问题 |

`tool_use_behavior` 的作用范围是：**已有工具结果为 error 后直接结束**。D6-04 的问题发生在第一次调用前，而且占位查询返回的是 empty，因此该回调不会阻止它。这不是回调失效，而是其设计范围不同。

## 4. 测试用例是否有问题

### 当前失败的判定合理

D6-04 明确表示没有提供流程编码，预期不调用工具并追问，与 D6 学习目标一致。`__MISSING__` 不是用户提供的编码，查询后再追问不满足这个要求。

不应通过以下方式让它变绿：

- 删除工具轨迹检查，只检查最终回答。
- 接受占位符查询，并将它视为正常空结果。
- 反复运行直到偶然全绿，再宣称已经稳定通过。

### 测试设计需要改进的部分

1. **混合了不同维度。** 当前用所有 checks 的逻辑与得到一个 passed，无法直接看出“回答正确、轨迹错误”。应保留总判定，同时分别展示回答结果、调用轨迹、执行边界的指标。
2. **脚本模型的证据范围有限。** `_day6_enqueue_case` 预先写好了调用及非错误答复。离线通过证明 SDK 接线、程序分支和报告正确，不能证明模型理解自然语言。这个限制应一直明确标注。
3. **结束策略已经变化。** 接入回调后，业务错误答复由程序生成。这可以验收系统正确结束，但不能继续解释为模型自主停止的证据。
4. **单轮不是稳定性评估。** 10 条全部通过可以作为一次验收结果，但单次通过不足以说明稳定；单次失败也不说明整个 MCP 链路失效。可在固定版本下做少量预先约定的重复评估，不应无限重跑。
5. **普通检查失败的诊断仍可增强。** 当前只在抛异常时保存 model_outputs；像本次“正常返回但检查失败”只保留答复和工具 Trace。后续可在这种失败上也保存已捕获的模型输出。
6. **运行版本证据不完整。** 报告尚未保存 Instructions、工具描述/Schema、模型设置和代码版本快照。当前文件时间早于本次报告，与修改后运行相符，但不能替代实际模型输入快照。

这些是测试质量改进项，不是放宽 D6-04 判定的理由。

### 5.1 参数格式合法，不代表参数有依据

Service 将非空、非纯空白字符串视为合法 engine_code。`__MISSING__` 满足这个格式条件，因此会查询 API。这符合现有 Service 契约，但不能承担“模型是否编造参数”的判断。

也不能简单改成“只允许 Mock 中已有的编码”：合法但没有记录的编码，本来就应该返回 empty，D6-07 正是在验收这一点。

### 5.2 输入护栏缺少来源信息

Day6Context 目前只有上限、调用记录和阻止记录，没有本轮问题或经过确认的参数。`check_day6_tool_call` 只检查已有错误、重复调用和总次数。第一次无依据查询既不重复，也没超额，当然会被放行。

### 5.3 输出结构只约束形状

Day6Answer 的类型和 extra='forbid' 校验不能证明“这个参数来自用户”，也不能保证“needs_input 前没有调用过工具”。这类要求需要检查调用过程和执行前条件。

### 5.4 当前仍把部分强约束交给模型自行遵守

业务错误停止已改为程序保证；缺参时不查询仍主要依赖模型阅读提示词。两者的可靠性机制不同。当前问题主要在这一点，而不是需要引入更多 Agent、Supervisor 或更复杂的工作流。

没有证据证明 SDK 强制要求每轮调用工具；当前 Agent 未配置 tool_choice='required'。也没有足够证据将问题归因为模型厂商接口兼容性。模型为何生成这个占位符的内部原因，现有记录不能证明。

## 6. 对前面处理方式的复盘

第一次把缺参字段写清楚是合理修正；给业务错误加入确定性的结束回调也有效。但在已经多次观察到模型忽略停止/缺参规则后，继续把补提示词作为主要解决办法，判断不够充分。

提示词和工具说明可以减少歧义，却不能代替执行前校验。前面应更早区分：

- 模型选择是否正确：Evals 记录真实偏差。
- 程序是否允许错误决策执行：执行层建立可验证边界。

## 7. 推荐下一步：小规模调整边界，而非继续追加提示词

针对当前只有两个查询工具的学习场景，推荐增加一个轻量的“查询参数准备与确认”步骤：

```text
自然语言问题
    ↓
得到结构化查询意图和可空参数
    ↓
程序校验参数是否存在、格式是否正确、是否有用户输入依据
    ├─ 缺参或没有依据 → needs_input，不提供可执行的业务查询
    └─ 参数确认 → 允许 Agent/MCP 查询
                         ↓
                  业务 error 由程序直接结束
```

学习阶段可以明确只支持用户显式给出的 task_id/engine_code 原值，并保留原文证据；例如用程序验证提取值确实出现于本轮输入。结构化提取本身仍可能出错，因此不能只把自由文本改成 JSON 就宣称已经保证正确。对否定、隐含指代、多轮确认等更复杂语义，需另外约定边界。

不建议新增 Supervisor、状态图或多套业务逻辑，也不建议使用测试编号、固定中文句子或 `__MISSING__` 黑名单来绕过测试。

如果采用输入护栏拒绝无依据参数，应区分“模型曾尝试错误调用，但程序拦截成功”和“模型根本没有请求错误工具”：系统执行边界可以通过，模型轨迹指标仍应记录失败。不能通过隐藏 blocked_calls 让原来的严格轨迹验收假通过。
